# 指定範圍驗證

GitHub Actions → CI → Run workflow 可選 `ui_scope`。`full` 執行全部 71 個 UI 案例；`part_a`、`part_b`、`part_c`、`part_d` 是依當次原始碼排序、不重複的四個分組。`expanded` 只執行新增 17 款完整對局路徑；也可以選單一遊戲。井字棋與四子棋的三種難度各自成為案例，每項仍驗證雙方先手及原有暫停／恢復／AI 斷言，避免六局共用單項逾時。普通 push 不自動跑模擬器 UI。

每組仍執行規則／存檔測試及真正 Simulator 編譯。`runner` 可選標準 `macos-15` 或 `macos-15-intel`，預設不變，無付費機器。通過 A、B 後修 C，不必無條件重跑 A、B；用 `baseline_run` 提供原始 Run IDs，`affected` 會依真實來源證據挑選未通過或受影響項目。

`part_a`～`part_d` 提供 `baseline_run` 時，先以相同來源集合重建未完成項目，再把它們分為四個不重複的分組；不提供來源時仍是原有完整四分組。預先選取紀錄標示 `affected-v1`，後續驗證重新讀取各個原始 ZIP、摘要、日誌與當時的來源集合，還原該分組原本應執行的項目。新近失敗會覆蓋舊通過；空分組或只有 iPad 略過項目的分組仍需跑真正 Home 案例。四組加總的當前 71 項覆蓋仍不可縮減。

跨 Run 證據以原始 XCTest 日誌、summary、來源 commit、Artifact 雜湊和逐案例相依原始碼重建。App 共用元件、Core、存檔、資源或未知依賴變動時，會保守地使相關／全部案例失效。測試斷言或共用測試工具有變動也必須重新驗證。不能拿任意綠色 Run、少數測試或不相符的舊原始碼假裝完整通過。

完成全部 71 個當前案例的可驗證覆蓋後，仍需同一候選版的 iPhone Visual 四項和 iPad 四張原生 PNG 加 22 款遊戲路徑證據。0.3.x TestFlight 禁止手動 QA 捷徑；不得把局部結果當成整體通過。`test-results` 保存原始執行日誌、xcresult 摘要及匯出的畫面／階層；大型原始 xcresult 另存 `simulator-xctest-results`，避免整個診斷 ZIP 超過下載工具的 512 MiB 限制。

將棋完整對局／重啟流程在 Intel 到真正升變獲勝及回看時已約 753 秒，因此該項明確保留 1800 秒上限；其他案例原有的 300／420／600 秒設定不變。只有兩對已審閱、完整檔案雜湊固定的執行腳本可將「僅提高 maximum ceiling」視為相同的已通過來源；default、測試選擇、開啟逾時、退出處理及所有其他內容必須完全一致。失敗或未執行的將棋不沿用，新的方法內容也有獨立雜湊，必須真正重跑。任何其他腳本改動仍讓相依證據失效。iPad 的最終四圖及 22 條驗證不以此豁免失敗。

上述工作完全 unsigned、不讀取 Apple 金鑰、不建立憑證。正式 TestFlight 仍限 main／手動入口及既有 match readonly 資產；只有驗證門檻通過後才執行使用者已授權的上傳。

## 保留未受影響的 iPhone 截圖

完整 CI 的當前覆蓋必須先獨立重建成功。之後若某個舊版 Visual Smoke 已真正通過四項測試，驗證器可逐項比對原始／當前的案例相依雜湊。只有四項都完全相符，才保留該次實際截圖來源。例如單獨修正新增棋類的渲染，不影響既有數獨、踩地雷、滑塊的四項畫面驗證時，可保留它們；共用元件、任何 Core、存檔、資源、執行腳本、測試輔助程式或已執行斷言改變都會拒絕沿用。

這不會把舊截圖改標為新 SHA。發布證據同時記錄原始 Run／來源 SHA、當前候選 SHA、四個相依雜湊及變動檔案；原工作流程仍必須成功，四項實際通過仍必須存在。未通過或取消的截圖工作不能用這條路徑變成通過。此路徑只適用四項 iPhone Visual Smoke；iPad 的四張原生 PNG 與全部遊戲路徑仍維持原本完整檢查。

歷史篩選 Menu 的固定修正只對十二條經審核、完全未開啟歷史畫面的路徑保留相依性：八項目錄與四項 iPhone 截圖。必須同時符合方法內容、全部 XCTest scaffold、整份其他執行來源及新舊歷史檔完整 hash，並以精確內容轉換重建新檔；`GameRecordText` 的共用格式化內容也保留在完整比對中。未知 helper、其他程式、模式或格式化變更都會拒絕這個例外。真正進入歷史的遊戲流程與鍵盤案例仍須重跑。四項截圖證據明列原始／新歷史檔 hash，不修改原圖或來源 SHA。

### 相同 iPad 工作的 CI 預啟動差異

完整成功的 iPad 4 張截圖＋22 條遊戲路徑可保留其真正來源 SHA，前提是候選完整 CI 已獨立驗證，且全部 26 個測試的內容、共用 helper、App、Core、種子、資源與專案相同。唯一新增的例外是上述固定 SHA-256 的執行腳本組合：移除已審核的同裝置預啟動區塊／還原 ceiling 後，完整內容必須精確等於基準；證據明列原／新／標準 hash。更改 App、斷言、選取項目、失敗處理、關閉 timeout、erase 或權限均不符合。原始整個 iPad 工作仍須成功，沒有部分通過或失敗豁免。新增四項正反向驗證；測試 fixture 不當作原生執行紀錄。

### V030 私有導覽列 helper 與整組時限

原生證據確認可見設定按鈕位於導覽列內、原私有捲動 helper 卻只接受列下內容。僅固定的兩個完整 scaffold 與精確逆向還原可把此差異限制於 final V030 XCTest 類別的 17 項；其他 54 項的實際通過紀錄仍須原始 ZIP、摘要、log、來源及相依性全部相符。未知 helper／setup／全域更動仍使全部失效。整組 CI 時限 90→180 分鐘同樣只接受固定完整 YAML 與單行逆向還原；取消、未完成、缺摘要或失敗案例不因時限調整得到通過資格。

### 有界的 XCTest 時間預算

Intel 實測完整目錄／版面案例超過 420 秒後會觸發 XCTest watchdog，影響下一項 App 啟停。已用固定來源、精確還原與負面測試核准一般 whole-case 600 秒及 V020 兩個同值設定；既有通過紀錄的字面斷言、遊戲資料與每步等待不變。另有固定 iPad job／boot／gallery 預算組合及 gallery maximum ceiling。未知時間、命令、權限、selector、模式或其他 setup 變化仍不等價。iPad-only 變更在手機略過時，加跑一個真實 Home 案例；失敗／取消／未執行紀錄不計為通過。

完整成功的 iPad 26 項來源，亦可在上述固定 V020 whole-case 420→600 秒及固定數獨方法 600→1800 秒差異下保留。驗證必須同時符合原、新完整 hash 與精確逆向還原，並列出 raw／canonical hash；26 項操作與斷言、其他 helper／setup、App、資料及模式仍受保護。這不合併部分 iPad 結果，也不改寫逐案例 CI 指紋：CI 中改過數獨方法仍須實際重跑。取消、失敗、缺摘要或未完整成功的來源仍拒絕使用。五項回歸測試涵蓋修改斷言、動作、setup、路徑、模式、非核准時限及偽造 after-hash 的拒絕行為；這些來源測試不是模擬器通過證據。
